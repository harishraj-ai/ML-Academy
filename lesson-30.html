1.From notebook to production

A model in a notebook helps nobody. It creates value when it runs reliably, every day, on new data, inside a product or a process, and keeps working as the world changes. MLOps (machine-learning operations) is the set of practices that makes that happen: packaging and versioning models, checking the data that comes in, serving predictions, monitoring for drift, retraining, and testing ML code like any other software.

Lesson 20 introduced pipelines and deployment; this lesson goes through the whole life cycle with working code. It uses a simulated loan-risk model, because what matters here is everything around the model.

The core idea

Treat a model as a product that decays. Make every version reproducible and traceable, refuse bad inputs, watch the inputs and the results continuously, and have a tested, routine way to retrain and roll out a new version, and to roll back.

2.The ML life cycle

  1. Develop: data, features, model, offline evaluation (everything up to now).
  2. Package and version: save the fitted pipeline with its metadata: data version, code version, library versions, metrics.
  3. Validate inputs: check every request against the expected schema.
  4. Serve: as a batch job (score all customers nightly) or online (an API answering in milliseconds).
  5. Monitor: input drift, prediction drift, and real performance once labels arrive.
  6. Retrain and redeploy: on a schedule or when monitoring says so, with tests and a gradual rollout.

3.Packaging and versioning a model

Save the whole pipeline (preprocessing and model together, Lesson 20), so the same transformations are applied in production. Alongside it, store metadata: a version number, the features it expects, its test metrics, the library versions used, and a fingerprint (hash) of the file so you can prove which model made a prediction:

import numpy as np
import pandas as pd
import joblib, json, hashlib, sklearn
from sklearn.pipeline import make_pipeline
from sklearn.preprocessing import StandardScaler
from sklearn.linear_model import LogisticRegression
from sklearn.metrics import roc_auc_score
rng = np.random.default_rng(0)
def make_loans(n, shift=0.0, flip=0.0):
    income = rng.normal(50 + shift, 15, n); debt = rng.normal(20, 8, n); age = rng.integers(21, 70, n)
    logit = (-0.08 + flip) * (income - 50) + 0.12 * (debt - 20) - 1.5
    return pd.DataFrame({"income": income, "debt": debt, "age": age}), (rng.random(n) < 1 / (1 + np.exp(-logit))).astype(int)
X_train, y_train = make_loans(5000)
X_test, y_test = make_loans(2000)
model = make_pipeline(StandardScaler(), LogisticRegression()).fit(X_train, y_train)
auc = roc_auc_score(y_test, model.predict_proba(X_test)[:, 1])
joblib.dump(model, "model_v1.joblib")
meta = {"version": "1.0.0", "features": list(X_train.columns), "test_auc": round(auc, 3),
        "sklearn": sklearn.__version__, "sha256": hashlib.sha256(open("model_v1.joblib", "rb").read()).hexdigest()[:12]}
json.dump(meta, open("model_v1.json", "w"), indent=1)
loaded = joblib.load("model_v1.joblib")
print("saved model", meta["version"], " test AUC", meta["test_auc"], " fingerprint length", len(meta["sha256"]))
print("reloaded model gives identical predictions:", bool(np.allclose(loaded.predict_proba(X_test), model.predict_proba(X_test))))

Output:

saved model 1.0.0  test AUC 0.818  fingerprint length 12
reloaded model gives identical predictions: True

The reloaded model gives identical predictions, which is the first thing to check after any save. Library versions matter: a model saved with one scikit-learn version may not load, or may behave differently, with another, so pin versions (a requirements.txt or a container image). Model registries such as MLflow keep these files, metadata and stages ("staging", "production") in one place.

4.Validating inputs

Production data is messier than training data: missing fields, wrong types, units changed upstream, impossible values. A model will happily return a confident prediction for nonsense, so check every input against a schema first and reject or flag what fails:

SCHEMA = {"income": (0, 500), "debt": (0, 200), "age": (18, 100)}
def validate(rows):
    problems = []
    for i, r in enumerate(rows):
        for col, (lo, hi) in SCHEMA.items():
            v = r.get(col)
            if v is None or not isinstance(v, (int, float)) or v != v:
                problems.append((i, col, "missing or not a number"))
            elif not lo <= v <= hi:
                problems.append((i, col, f"{v} outside [{lo}, {hi}]"))
    return problems
incoming = [{"income": 62.0, "debt": 18.5, "age": 34}, {"income": 48.0, "age": 29},
            {"income": -5.0, "debt": 30.0, "age": 41}, {"income": 55.0, "debt": "12", "age": 230}]
for p in validate(incoming):
    print("row", p[0], "·", p[1], "·", p[2])

Output:

row 1 · debt · missing or not a number
row 2 · income · -5.0 outside [0, 500]
row 3 · debt · missing or not a number
row 3 · age · 230 outside [18, 100]

Each problem is caught before the model sees it: a missing debt value, a negative income, a number sent as text, and an age of 230. Decide in advance what happens to bad rows: reject the request, use a safe default, or send it to a person. Log them, too, because a sudden rise in bad inputs usually means something broke upstream.

5.Detecting data drift

Data drift means the inputs no longer look like the training data. Two common measures compare a feature's training and live distributions:

  • The population stability index (PSI): bin the feature by training quantiles and sum $(a - e)\ln(a/e)$ over bins, where $e$ and $a$ are the training and live shares. Rules of thumb: below 0.1 stable, 0.1 to 0.25 worth watching, above 0.25 a major shift.
  • The Kolmogorov–Smirnov test: the largest gap between the two cumulative distributions, with a p-value. With large samples even trivial shifts become "significant", so look at the statistic's size too.
from scipy import stats
def psi(expected, actual, bins=10):
    edges = np.quantile(expected, np.linspace(0, 1, bins + 1)); edges[0], edges[-1] = -np.inf, np.inf
    e = np.histogram(expected, edges)[0] / len(expected); a = np.histogram(actual, edges)[0] / len(actual)
    e, a = np.clip(e, 1e-4, None), np.clip(a, 1e-4, None)
    return float(np.sum((a - e) * np.log(a / e)))
X_live, _ = make_loans(2000, shift=-12)                 # incomes have fallen
for col in X_train.columns:
    ks = stats.ks_2samp(X_train[col], X_live[col])
    print(f"{col:6s}  PSI {psi(X_train[col], X_live[col]):.3f}   KS statistic {ks.statistic:.3f}   p-value {ks.pvalue:.3g}")

Output:

income  PSI 0.612   KS statistic 0.312   p-value 1.12e-123
debt    PSI 0.003   KS statistic 0.021   p-value 0.536
age     PSI 0.007   KS statistic 0.015   p-value 0.892

Incomes in the live data have fallen: income's PSI is 0.612, a major shift, and the KS statistic is 0.312. Debt and age are stable (PSI under 0.01). Drift doesn't always hurt performance, but it's an early warning that arrives long before labels do. Monitor the model's predictions in the same way: a sudden change in the share of high-risk scores is easy to spot.

6.Try it: measuring drift

Shift the live data's mean or change its spread, and watch the PSI and the verdict. Notice that a change in spread alone, with the same average, is also caught.

7.Concept drift and retraining

Sometimes the inputs look the same but the relationship between inputs and outcome changes: concept drift. After an economic shock, the same income may mean a different risk. Only real outcomes reveal it, so monitor performance as labels arrive. Here, from month 5, the effect of income fades and then reverses. One model is never retrained; the other is retrained each month on the previous month's labelled loans:

# 12 months of new loans; from month 5 the effect of income fades and then reverses (concept drift).
static, retrained, current = [], [], model
for month in range(1, 13):
    flip = 0.0 if month < 5 else 0.02 * (month - 4)
    Xm, ym = make_loans(1500, flip=flip)
    static.append(roc_auc_score(ym, model.predict_proba(Xm)[:, 1]))
    retrained.append(roc_auc_score(ym, current.predict_proba(Xm)[:, 1]))
    current = make_pipeline(StandardScaler(), LogisticRegression()).fit(Xm, ym)   # retrain on this month's labels
print("AUC, never retrained:   ", [round(a, 2) for a in static])
print("AUC, retrained monthly: ", [round(a, 2) for a in retrained])

Output:

AUC, never retrained:    [0.82, 0.83, 0.82, 0.84, 0.77, 0.76, 0.71, 0.65, 0.58, 0.55, 0.46, 0.41]
AUC, retrained monthly:  [0.82, 0.83, 0.82, 0.84, 0.77, 0.77, 0.74, 0.72, 0.73, 0.79, 0.78, 0.83]

The original model's AUC falls from 0.82 to 0.41, worse than guessing, while the regularly retrained model recovers to 0.83, lagging a month behind the change. Retraining strategies range from a fixed schedule (weekly, monthly) to triggers: retrain when drift or performance crosses a threshold. Either way, validate each new model on recent data before it replaces the old one, and keep the old one ready for a rollback.

8.Testing ML code

ML systems need ordinary unit tests (does the feature function handle missing values?) plus tests of the model's behaviour:

  • Minimum quality: the metric on a fixed test set is above a threshold.
  • Directional tests: changing an input in a known direction moves the prediction the right way.
  • Invariance tests: changing something that shouldn't matter (or mustn't, such as a protected attribute) doesn't change the prediction much.
def report(name, ok):
    print(("PASS " if ok else "FAIL ") + name)
base = pd.DataFrame({"income": [50.0], "debt": [20.0], "age": [40]})
p0 = model.predict_proba(base)[0, 1]
report("minimum quality: test AUC above 0.70", meta["test_auc"] > 0.70)
report("directional: more debt means higher risk", model.predict_proba(base.assign(debt=35.0))[0, 1] > p0)
report("directional: more income means lower risk", model.predict_proba(base.assign(income=80.0))[0, 1] < p0)
report("invariance: age changes risk by under 2 points", abs(model.predict_proba(base.assign(age=65))[0, 1] - p0) < 0.02)
report("output is a valid probability", 0 <= p0 <= 1)

Output:

PASS minimum quality: test AUC above 0.70
PASS directional: more debt means higher risk
PASS directional: more income means lower risk
PASS invariance: age changes risk by under 2 points
PASS output is a valid probability

All five checks pass. Run them automatically (with pytest, as in the course's code zip) every time code, data or the model changes, as part of continuous integration: a failing test should block a deployment, just as in any other software.

Log every prediction with the input, the output, the model version and a timestamp: you'll need it to debug, to monitor, to join with outcomes later for retraining, and to explain decisions to the people affected.

10.In Python: a prediction service function

The core of an online service, without a web framework: validate the request, predict with the pipeline, and return the answer with the model version, logging everything. A FastAPI or Flask endpoint would just call this function:

import json, time
import numpy as np
import pandas as pd
from sklearn.pipeline import make_pipeline
from sklearn.preprocessing import StandardScaler
from sklearn.linear_model import Ridge

df = pd.read_csv("houses.csv")   # download it from Lesson 1
FEATURES = ["size_m2", "bedrooms", "dist_km", "age_yrs"]
model = make_pipeline(StandardScaler(), Ridge(1.0)).fit(df[FEATURES], df["price_lakh"])
VERSION, LOG = "houses-1.0.0", []

def handle(request_json):
    req = json.loads(request_json)
    missing = [f for f in FEATURES if not isinstance(req.get(f), (int, float))]
    if missing:
        result = {"error": "missing or invalid: " + ", ".join(missing), "model": VERSION}
    else:
        price = model.predict(pd.DataFrame([req])[FEATURES])[0]
        result = {"price_lakh": round(float(price), 1), "model": VERSION}
    LOG.append({"time": time.time(), "request": req, "response": result})
    return json.dumps(result)

print(handle('{"size_m2": 110, "bedrooms": 3, "dist_km": 6, "age_yrs": 4}'))
print(handle('{"size_m2": 110, "bedrooms": "three", "dist_km": 6}'))
print("requests logged:", len(LOG))

Output:

{"price_lakh": 91.9, "model": "houses-1.0.0"}
{"error": "missing or invalid: bedrooms, age_yrs", "model": "houses-1.0.0"}
requests logged: 2

A valid request gets a price and the model version; an invalid one gets a clear error instead of a made-up prediction, and both are logged. In a real service, the log would go to a database or a monitoring system, the model would be loaded from the registry by version, and the function would be wrapped in an HTTP endpoint with authentication.

11.Running example: Chennai Homes

Package the house-price pipeline as a versioned bundle: the fitted pipeline, its feature list and a version number, saved with joblib and loaded back as a service would. The reloaded model predicts 78.9 lakh for a 95 m², 2-bedroom home 5 km out and 3 years old, and a simple range check confirms every input lies within the training data. With only 12 training homes, inputs outside those ranges deserve a warning rather than a confident answer.

Same 12 houses as Lesson 1. With so little data, treat the numbers as an illustration of the method, not as reliable estimates.

import pandas as pd
import numpy as np
df = pd.read_csv("houses.csv")   # download it from Lesson 1
import joblib
from sklearn.pipeline import make_pipeline
from sklearn.preprocessing import StandardScaler
from sklearn.linear_model import Ridge
cols = ["size_m2", "bedrooms", "dist_km", "age_yrs"]
pipe = make_pipeline(StandardScaler(), Ridge(1.0)).fit(df[cols], df.price_lakh)
joblib.dump({"model": pipe, "features": cols, "version": "1.0.0"}, "price_model.joblib")
bundle = joblib.load("price_model.joblib")
new = pd.DataFrame({"size_m2": [95], "bedrooms": [2], "dist_km": [5], "age_yrs": [3]})
print("model", bundle["version"], "predicts", round(float(bundle["model"].predict(new[bundle["features"]])[0]), 1), "lakh")
ranges = {c: (df[c].min(), df[c].max()) for c in cols}
print("inside the training range:", {c: bool(ranges[c][0] <= new[c].iloc[0] <= ranges[c][1]) for c in cols})

Output:

model 1.0.0 predicts 78.9 lakh
inside the training range: {'size_m2': True, 'bedrooms': True, 'dist_km': True, 'age_yrs': True}
Where this is used
  • Credit, fraud and churn models that run every day
  • Demand forecasts feeding stock and staffing systems
  • Any model whose predictions reach customers or automated decisions

Choose it when: Whenever a model will run repeatedly on new data, outside a one-off analysis.

Think twice when: the analysis is a one-off report: then reproducibility matters, but monitoring and serving don't.

Misconceptions to unlearn

MythOnce a model is deployed, the work is done.

RealityModels decay as the world changes; monitoring and retraining are ongoing work.

MythIf input drift is detected, the model must be retrained.

RealityDrift is a warning; check whether performance has actually dropped before acting.

MythA high test score means the model is ready for production.

RealityIt also needs input validation, behavioural tests, monitoring, logging and a rollback plan.

Responsible AI · Accountability after launch

Harm from models often appears after deployment: inputs shift for one region, a data pipeline breaks for one group, a model slowly drifts. Monitor metrics by group as well as overall, keep prediction logs so individual decisions can be explained and challenged, publish a model card with intended uses and limits, and make sure someone is responsible for acting when monitoring raises an alarm.

12.Questions beginners often ask

How often should I retrain?

It depends on how fast the world changes. Start with a schedule that matches the pace (weekly for fraud, monthly or quarterly for slow-moving risk), then add triggers based on drift and performance. Always compare a new model with the current one before switching.

Do I need special MLOps tools?

Not to start. Version code with git, pin library versions, save pipelines with metadata, log predictions, and schedule jobs. Tools such as MLflow, feature stores and monitoring platforms help as the number of models grows.

What's the difference between data drift and concept drift?

Data drift: the inputs' distribution changes. Concept drift: the relationship between inputs and outcome changes. Data drift can be seen immediately; concept drift needs outcomes.

What should a model card contain?

What the model is for and not for, the training data, metrics overall and by group, known limitations, the version, and who to contact.

Common mistakes to avoid
  • Saving the model without its preprocessing, then re-implementing the preprocessing in production.
  • Not recording library versions, so the model can't be reloaded later.
  • Predicting on invalid inputs instead of rejecting or flagging them.
  • Monitoring only inputs, never actual performance once outcomes arrive.
  • Replacing a model without comparing it with the current one on recent data.
Interview corner

Hidden questions — answer in your head first, then open.

What's the difference between data drift and concept drift?

The trap: Using the terms interchangeably.

Data drift: the distribution of inputs changes (incomes fall). Concept drift: the relationship between inputs and the outcome changes (the same income now means a different risk). Data drift can be detected immediately from inputs; concept drift only shows in performance once outcomes arrive.

What would you log for every prediction a production model makes?

The trap: "Just the prediction."

A request ID and timestamp, the input features (or a reference to them), the prediction and score, the model version, and latency, plus any validation failures. That supports debugging, monitoring of inputs and outputs, joining with outcomes later for evaluation and retraining, audits and explanations to affected people, while respecting privacy rules on what may be stored.

How do you safely replace a production model with a new one?

The trap: "Deploy it if its test score is higher."

Validate offline on recent data with a paired comparison and confidence interval; run behavioural tests; deploy in shadow mode to compare predictions on live traffic; then a canary or A/B rollout measuring the business metric and guardrails; keep the old model ready for instant rollback; monitor closely after full release.

Your drift monitor alerts every day on several features. What's going wrong, and how do you fix it?

The trap: "Retrain every day."

Probably it alerts on p-values from large samples, so trivial shifts are significant. Alert on effect sizes (PSI, KS statistic, standardised mean change) with thresholds tied to business impact, prioritise features by importance to the model, aggregate over sensible windows, and confirm with performance metrics when labels arrive. Tune thresholds on historical data to an acceptable false-alarm rate.

13.Key takeaways

  • Save the whole pipeline with metadata: version, features, metrics, library versions and a fingerprint.
  • Validate inputs against a schema before predicting; log and handle failures deliberately.
  • Monitor data drift (PSI, KS) early and performance when labels arrive.
  • Concept drift needs retraining; validate new models and keep rollbacks ready.
  • Test model behaviour: minimum quality, directional and invariance tests, in CI.
  • Roll out with shadow or canary deployments, and log every prediction.

15.Going deeper: drift alarms and champion–challenger tests

In plain wordsWhy a drift test's p-value raises alarms about harmless changes once you have lots of data, while the PSI measures how big a shift really is, and how bootstrapping shows whether a new model's small improvement is real before replacing the current one.

Intermediate · skip on a first read

Two judgement calls in monitoring: why statistical drift tests raise false alarms with big data, and how to decide whether a new model is really better than the one in production.

You'll need: this lesson, hypothesis tests from Lesson 4's "Going deeper", and the bootstrap.

Significant is not the same as important

Here the live data is shifted by a tiny, harmless 0.03 standard deviations. Watch what happens to the KS test's p-value and to the PSI as the live sample grows:

import numpy as np
from scipy import stats
rng = np.random.default_rng(1)
train = rng.normal(0, 1, 50000)
for n in [500, 5000, 50000]:
    live = rng.normal(0.03, 1, n)                                    # a tiny, harmless shift
    ks = stats.ks_2samp(train, live)
    edges = np.quantile(train, np.linspace(0, 1, 11)); edges[0], edges[-1] = -np.inf, np.inf
    e, a = np.histogram(train, edges)[0] / len(train), np.histogram(live, edges)[0] / n
    psi = float(np.sum((a - e) * np.log(a / e)))
    print(f"live sample {n:6d}: KS p-value {ks.pvalue:.3g}   PSI {psi:.4f}")

Output:

live sample    500: KS p-value 0.158   PSI 0.0289
live sample   5000: KS p-value 0.0375   PSI 0.0031
live sample  50000: KS p-value 1.08e-06   PSI 0.0021

With 500 rows the KS test sees nothing (p = 0.158); with 50,000 rows the same tiny shift gives p ≈ $10^{-6}$, an "alarm" about nothing. The PSI stays tiny throughout (below 0.03), because it measures the size of the shift, not how surely it exists; with small samples it's a little noisier. In production, alert on effect sizes (PSI, the KS statistic itself, change in mean in standard deviations) with thresholds tied to impact, not on p-values, or every big feature will alarm every day.

Is the challenger really better?

A new model scores higher on a test set. Before replacing the champion, check whether the difference is bigger than the noise. Bootstrapping the test set (resampling it with replacement many times) gives an interval for the improvement:

from sklearn.metrics import roc_auc_score
m = 3000
y = rng.integers(0, 2, m)
champion = y * 1.0 + rng.normal(0, 1.2, m)                          # current model's scores
challenger = y * 1.0 + rng.normal(0, 1.1, m)                        # new model, slightly better
diffs = []
for _ in range(1000):                                               # bootstrap the AUC difference
    idx = rng.integers(0, m, m)
    diffs.append(roc_auc_score(y[idx], challenger[idx]) - roc_auc_score(y[idx], champion[idx]))
lo, hi = np.percentile(diffs, [2.5, 97.5])
print("AUC champion", round(roc_auc_score(y, champion), 3), " challenger", round(roc_auc_score(y, challenger), 3))
print("95% interval for the improvement:", round(lo, 3), "to", round(hi, 3))

Output:

AUC champion 0.725  challenger 0.728
95% interval for the improvement: -0.022 to 0.027

The challenger's AUC is 0.003 higher, but the 95% interval for the improvement runs from −0.022 to 0.027: the data can't tell the two apart. Switching would add risk for no proven gain. Stronger evidence comes from more test data, comparing on the same rows (paired, as here), and a shadow or canary deployment that measures the business outcome, not just the offline metric.

Effect sizes don't grow just because the sample does.

Exercise 3By hand

Name one directional test and one invariance test for a house-price model.

Show solution
Directional: increasing size (all else equal) shouldn't lower the price. Invariance: changing the listing ID or the seller's name shouldn't change the price.
