Target encoding: how much leakage can fake

Target encoding replaces each category with the average target for that category. It's powerful for categories with many levels (postcodes, product IDs), but if the averages are computed using the rows you then evaluate on, each row's own target leaks into its feature. Here a category with 2,000 levels has no real relationship with the target, so the honest accuracy is 50%:

The naive encoding reports 73.1% accuracy on pure noise: with about 2.5 rows per level, each level's average is dominated by the rows' own labels. Inside the pipeline, scikit-learn's TargetEncoder is refitted on each training fold, and also uses cross-fitting during training (each training row is encoded using averages from the other internal folds), so the estimate drops to the honest 49.7%. Two further safeguards it applies: smoothing towards the overall average for rare levels, much like the Bayesian shrinkage in Lesson 4's "Going deeper", and handling of unseen levels.

One pipeline for mixed data

Real tables mix numbers, categories and text, each needing different preprocessing. ColumnTransformer applies the right steps to the right columns, and putting it inside a pipeline means every step is fitted on training folds only:

Four numeric columns (one with a missing value, imputed with the training median and standardised), one-hot encoded areas and a TF-IDF of the descriptions give 30 columns, fed to ridge regression. Cross-validated on the 12 Chennai homes the mean error is about 7.0 lakh, which with so few homes is only an illustration. The important point is structural: the whole object can be cross-validated, tuned with GridSearchCV (parameter names such as columntransformer__num__simpleimputer__strategy) and saved as one file, so training and serving can't drift apart.

Grid search vs random search

A grid tries every combination of a few values per setting. Random search samples settings from ranges you specify. With the same budget it usually does as well or better, because typically only one or two settings really matter: a 3×3×2 grid tests just 3 distinct values of each, whereas 18 random draws test 18 different values of every setting (Bergstra and Bengio, 2012). Sample learning rates and penalties on a log scale (loguniform), since they matter by orders of magnitude.

Here, with 18 settings each, both reach about the same best cross-validated accuracy (0.975 and 0.972, a difference well within noise). The advantage of random search grows with the number of settings: the grid's size multiplies, the random budget doesn't. Beyond random search, Bayesian optimisation (for example Optuna's TPE sampler) uses past results to choose promising settings next, and successive halving (HalvingRandomSearchCV) gives every candidate a little data and only the best ones more.

Keeping track of experiments

After a few weeks a project has hundreds of runs. Without records, nobody can say which data, code and settings produced the model in production. Good practice:

  • Log every run: parameters, metrics, the code version (a git commit), the data version, the random seed and the library versions. Tools such as MLflow and Weights & Biases do this with a few lines.
  • Version the data as well as the code (for example with DVC, or by storing immutable dated snapshots).
  • Save the whole pipeline, not just the model, together with a model card: intended use, training data, metrics by subgroup (Lesson 21) and known limitations.
  • Keep the test set out of the loop. Every decision taken by looking at test results makes them optimistic (Lesson 4's "Going deeper" on multiple testing).
