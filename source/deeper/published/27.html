Alternating least squares

Picture it

Solving for two unknowns at once is hard; solving for one while the other is held still is easy. So fix the items and work out every user's tastes, then fix the users and work out every item's, and keep alternating.

With the item factors $Q$ fixed, each user's vector is a small ridge regression on the items they rated, with a direct answer:

$$\mathbf{p}_u = (Q_u^\top Q_u + \lambda I)^{-1} Q_u^\top \mathbf{r}_u$$

In words: "which taste vector best explains this user's ratings, with a small ridge penalty". Then fix $P$ and solve for every item the same way. One user-step plus one item-step is a sweep.

Worked example — one user with one factor
  1. Items rated have factors 1, 2, 3; the user rated them 2, 4, 6. $\lambda=0$.
  2. $Q^\top Q=1+4+9=14$; $Q^\top r=2+8+18=28$.
  3. $p_u=28/14=2$: this user's taste is 2, and $2\times$ each item's factor reproduces the ratings exactly.
import numpy as np
rng = np.random.default_rng(0)
n_users, n_items, k = 200, 40, 3
P_true, Q_true = rng.normal(0, 1, (n_users, k)), rng.normal(0, 1, (n_items, k))
R = P_true @ Q_true.T + rng.normal(0, 0.3, (n_users, n_items))
mask = rng.random((n_users, n_items)) < 0.2            # only 20% of ratings observed
test = (rng.random((n_users, n_items)) < 0.25) & mask
train = mask & ~test
P, Q, lam = rng.normal(0, 0.1, (n_users, k)), rng.normal(0, 0.1, (n_items, k)), 1.0
for sweep in range(1, 9):
    for u in range(n_users):                           # fix Q, solve a small ridge problem per user
        Qi = Q[train[u]]
        P[u] = np.linalg.solve(Qi.T @ Qi + lam * np.eye(k), Qi.T @ R[u, train[u]])
    for i in range(n_items):                           # fix P, solve per item
        Pu = P[train[:, i]]
        Q[i] = np.linalg.solve(Pu.T @ Pu + lam * np.eye(k), Pu.T @ R[train[:, i], i])
    if sweep in (1, 2, 4, 8):
        rmse = np.sqrt(np.mean((R - P @ Q.T)[test] ** 2))
        print("sweep", sweep, " test RMSE", round(rmse, 3))

Output:

sweep 1  test RMSE 1.635
sweep 2  test RMSE 1.456
sweep 4  test RMSE 0.964
sweep 8  test RMSE 0.762

How to read it: with 3 true factors and 20% of ratings observed, test RMSE falls from 1.635 after one sweep to 0.762 after eight. Every user's (and item's) update is independent, so ALS runs in parallel easily, which is why Spark's recommender uses it. A weighted version (Hu, Koren and Volinsky) handles implicit feedback, where every unclicked item counts as a weak zero.

Measuring popularity bias

Picture it

A bookshop that only puts bestsellers in the window. Sales look fine, but most of the books are never shown, niche readers are ignored, and new authors never get a chance.

Accuracy metrics reward recommending popular items, because they're most likely to appear in anyone's held-out set. Two simple health checks: catalogue coverage and the average popularity of recommended items.

popularity = train.sum(axis=0)                         # how many users interacted with each item
scores_pop = np.tile(popularity, (n_users, 1)).astype(float)
scores_mf = P @ Q.T
for name, S in [("popular", scores_pop), ("matrix factorisation", scores_mf)]:
    S = np.where(train, -np.inf, S)                    # don't recommend items already seen
    top = np.argsort(-S, axis=1)[:, :5]
    coverage = len(np.unique(top)) / n_items
    avg_pop = popularity[top].mean()
    print(f"{name:21s} catalogue coverage {coverage:.2f}   average popularity of recommended items {avg_pop:.1f}")
print("average popularity across all items:", round(popularity.mean(), 1))

Output:

popular               catalogue coverage 0.30   average popularity of recommended items 38.7
matrix factorisation  catalogue coverage 0.85   average popularity of recommended items 30.4
average popularity across all items: 29.2
Worked example — reading the rows
  1. Popularity baseline: reaches only 30% of the catalogue; recommended items are liked by 38.7 users on average vs 29.2 overall.
  2. Matrix factorisation: 85% coverage, popularity 30.4, close to average.

Track these next to precision@k: a change that raises precision slightly but halves coverage can make the product worse for users and for the people who supply the items.

In one breath

ALS fits matrix factorisation by alternating simple ridge regressions for users and items, which parallelises well; and always check coverage and popularity of recommendations, not just accuracy.

Hidden questions — answer in your head first, then open.

SGD or ALS for matrix factorisation: how do you choose?

The trap: Saying one is always better.

SGD is simple, handles explicit ratings and extra terms (biases, side features) easily and is cheap per step, but needs a tuned learning rate. ALS has closed-form steps, needs no learning rate, parallelises across users and items, and handles implicit feedback with all unobserved pairs efficiently, which is why it's common on Spark. Both need regularisation tuned on validation data.
