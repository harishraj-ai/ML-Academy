16.Going deeper: indexes, NULL logic and rolling features

In plain wordsThree SQL traps for ML work: slow queries (indexes and query plans), rows that silently disappear (NULL means "unknown", so comparisons with it are neither true nor false), and rolling "last 7 days" features that leak the answer.

New words for this section
  • Full scan: reading every row of a table.
  • Index: a sorted lookup structure, like the index at the back of a book.
  • Query plan: the strategy the database chose to answer a query.
  • NULL: "unknown": not zero, not empty, just not known.
  • Window frame: the set of nearby rows a window function looks at.

Indexes and query plans

Picture it

Finding every mention of "tax" in a book: read every page (a full scan) or look it up in the index at the back and jump straight to the right pages. A database index works the same way.

Worked example — scan vs index
  1. 200,000 viewings. A full scan checks all 200,000 rows.
  2. A B-tree index halves the search at each level: about $\log_2(200{,}000)\approx18$ steps to reach house 42.
  3. Then it reads just that house's 37 rows.

EXPLAIN QUERY PLAN shows which strategy the database picked:

import sqlite3
import numpy as np
import pandas as pd

# A bigger events table: 200,000 viewings of 5,000 houses
rng = np.random.default_rng(0)
con = sqlite3.connect(":memory:")
pd.DataFrame({"house_id": rng.integers(1, 5001, 200000), "day": rng.integers(1, 366, 200000)}).to_sql("viewings", con, index=False)
q = "SELECT COUNT(*) FROM viewings WHERE house_id = 42"
print("plan without an index:", con.execute("EXPLAIN QUERY PLAN " + q).fetchall()[0][-1])
con.execute("CREATE INDEX idx_house ON viewings(house_id)")
print("plan with an index:   ", con.execute("EXPLAIN QUERY PLAN " + q).fetchall()[0][-1])
print("viewings of house 42:", con.execute(q).fetchone()[0])

Output:

plan without an index: SCAN viewings
plan with an index:    SEARCH viewings USING COVERING INDEX idx_house (house_id=?)
viewings of house 42: 37

How to read it: the plan changes from SCAN (read everything) to SEARCH ... USING COVERING INDEX (jump to house 42's 37 rows). "Covering" means the index alone holds every column the query needs, so the table isn't read at all.

Index the columns you filter and join on most, but not everything: indexes take space and slow down inserts. In cloud warehouses (BigQuery, Snowflake) the equivalents are partitioning and clustering, and you pay for data scanned, so filtering on the partition column (usually a date) saves real money.

NULL: three-valued logic

Picture it

Ask "is the unknown discount bigger than 5?" The honest answer is "don't know". Ask "is it NOT bigger than 5?" Still "don't know". SQL keeps only rows where the answer is a definite yes, so rows with unknown values drop out of both questions.

In SQL every comparison can be true, false or unknown. WHERE keeps only true. Four rows with discounts 10, NULL, 0, NULL:

# NULL is "unknown": comparisons with it are neither true nor false
t = pd.DataFrame({"id": [1, 2, 3, 4], "discount": [10, None, 0, None]})
t.to_sql("t", con, index=False)
conds = {"discount > 5": "discount > 5", "NOT (discount > 5)": "NOT (discount > 5)",
         "discount equals NULL": "discount = NULL", "discount IS NULL": "discount IS NULL"}
for label, cond in conds.items():
    print(f"{label:21} -> rows {[r[0] for r in con.execute(f'SELECT id FROM t WHERE {cond}')]}")
print("COUNT(*), COUNT(discount), AVG(discount):", con.execute("SELECT COUNT(*), COUNT(discount), AVG(discount) FROM t").fetchone())

Output:

discount > 5          -> rows [1]
NOT (discount > 5)    -> rows [3]
discount equals NULL  -> rows []
discount IS NULL      -> rows [2, 4]
COUNT(*), COUNT(discount), AVG(discount): (4, 2, 5.0)
Worked example — reading each line
  1. discount > 5: row 1 (10). Rows 2 and 4 are unknown, so dropped.
  2. NOT (discount > 5): only row 3. "Not unknown" is still unknown, so rows 2 and 4 vanish again.
  3. discount = NULL: nothing, ever. Use IS NULL: rows 2 and 4.
  4. AVG(discount) $=(10+0)/2=5.0$: the NULLs are skipped. Treating missing as 0 would give $(10+0+0+0)/4=2.5$.

Aggregates skip NULLs: COUNT(discount) is 2, not 4, and AVG averages only the known values. Decide explicitly what missing means, and use COALESCE(discount, 0) only when missing truly means zero.

Rolling features with window frames

Picture it

A 7-day rolling total is a sliding window: today plus the six days before. Slide it forward one day and the oldest day falls out while the newest comes in. LAG simply looks one row back.

ROWS BETWEEN 6 PRECEDING AND CURRENT ROW limits the window to the current row and the six before it. Together with LAG this builds standard time-series features (Lesson 26) in the database:

# Rolling, point-in-time features with a window frame: viewings in the 7 days up to and including each day
daily = pd.DataFrame({"house_id": [1] * 10, "day": range(1, 11), "views": [0, 2, 1, 0, 3, 1, 0, 0, 4, 1]})
daily.to_sql("daily", con, index=False)
q = """SELECT day, views,
              SUM(views) OVER (PARTITION BY house_id ORDER BY day ROWS BETWEEN 6 PRECEDING AND CURRENT ROW) AS views_7d,
              LAG(views) OVER (PARTITION BY house_id ORDER BY day) AS views_yesterday
       FROM daily"""
print(pd.read_sql(q, con).to_string(index=False))

Output:

 day  views  views_7d  views_yesterday
   1      0         0              NaN
   2      2         2              0.0
   3      1         3              2.0
   4      0         3              1.0
   5      3         6              0.0
   6      1         7              3.0
   7      0         7              1.0
   8      0         7              0.0
   9      4         9              0.0
  10      1         9              4.0
Worked example — day 9's 7-day total
  1. Window = days 3 to 9.
  2. Views: $1+0+3+1+0+0+4=9$.
  3. Day 1 has no previous day, so views_yesterday is NULL (NaN in pandas).
Two leaks to avoid
  • If day $d$'s prediction is made at the start of day $d$, end the frame at 1 PRECEDING, not CURRENT ROW, or that day's own views leak in.
  • ROWS counts rows, not days. If days are missing, use RANGE BETWEEN 6 PRECEDING AND CURRENT ROW on a numeric day column, or fill in missing days first.
In one breath

Index the columns you filter and join on and read the query plan; remember NULL makes comparisons unknown, so handle missing values explicitly; and build rolling features with window frames that only look at the past.

Interview corner · intermediate

Hidden questions — answer in your head first, then open.

A query on a large table is slow. What do you check first?

The trap: Jumping straight to buying a bigger machine.

Read the query plan (EXPLAIN): is it scanning the whole table? Check that filter and join columns are indexed (or, in a warehouse, that you filter on the partition column), that you select only the needed columns, and that joins aren't exploding rows. Filter early, aggregate before joining, and avoid functions on indexed columns in WHERE, which can stop the index being used.

Explain how NULL behaves in comparisons, NOT, COUNT and AVG.

The trap: Treating NULL like zero or like false.

NULL is unknown, so any comparison with it (=, <, >) is unknown, and NOT unknown is still unknown; WHERE keeps only true rows, so NULL rows vanish from both a condition and its negation. Use IS NULL. COUNT(*) counts rows, COUNT(col) counts non-NULLs, and AVG/SUM ignore NULLs. NULL in an IN list or a NOT IN subquery can make NOT IN return no rows at all.

How would you compute "purchases in the previous 30 days" for every customer-day without leakage?

The trap: Using a window that includes the current day.

Build a daily table per customer (filling days with no purchases), then use a window frame that ends before the current row, e.g. SUM(purchases) OVER (PARTITION BY customer ORDER BY day ROWS BETWEEN 30 PRECEDING AND 1 PRECEDING), or a RANGE frame on dates. Validate on a time-based split. The same logic must run identically in training and in production, which is what feature stores provide.

Check your understanding: going deeper

1. What does an index on viewings(house_id) let the database do?

A B-tree index finds matching rows in about log n steps.

2. A column has values 10, NULL, 0, NULL. How many rows does WHERE NOT (x > 5) return?

Only the 0 row. For NULL rows, x > 5 is unknown and so is its negation, and WHERE keeps only true conditions.

3. What is AVG(x) for the values 10, NULL, 0, NULL?

Aggregates skip NULLs: the average of 10 and 0 is 5.

4. A prediction for day d is made at the start of day d. Which frame avoids leakage in a 7-day sum?

The window must end before the current day, whose data isn't known yet.

5. Why might ROWS BETWEEN 6 PRECEDING AND CURRENT ROW not give a 7-day window?

ROWS counts rows. Fill in missing days, or use a RANGE frame on a numeric day column.
