Part 2 · Lesson 5

Data, features & generalization

1The real goal: new data

In Lesson 1, learning meant "find the parameters that make the loss small". True, but there's a catch: we already know the answers for the training data. A model is only useful if it predicts well on data it has never seen: next month's houses, tomorrow's emails, next week's patient. That ability is called generalization, and it's the single most important idea in ML.

The exam story
Student A memorises the 50 practice answers. Student B learns the methods. Both get 100% on the practice questions. On the real exam (new questions) A fails, B passes. A memorising model is student A; we need a fair exam to tell them apart.

2What a dataset looks like

A table: one row per example, one column per feature, plus a label column. In maths: features $X$ of shape $n\times d$ ($n$ examples, $d$ features) and labels $\mathbf{y}$ of length $n$.

Kinds of features

  • Numerical: measured amounts. Continuous (size, temperature) or discrete counts (bedrooms).
  • Categorical: one of a fixed set (city, colour). Must be turned into numbers (Lesson 20).
  • Ordinal: categories with an order: small < medium < large, 1–5 stars.
  • Binary: yes/no → 1/0.
  • Text, images, audio: must be turned into numbers first (word counts, pixel values).

Data quality beats clever algorithms. A model can only learn patterns that are really in the data. Common problems:

  • Missing values: blanks in the table.
  • Errors and outliers: a house listed at 5 m², a typo adding three zeros to a price.
  • Too few examples: can't tell real patterns from coincidences.
  • Unrepresentative data: trained on city flats, then asked about rural farmhouses.
  • Wrong labels: mislabelled examples teach the wrong lesson.
The i.i.d. assumption
Most ML assumes examples are independent and identically distributed: in plain words, future data will look like past data. When that stops being true (fashions change, a new competitor arrives), models quietly get worse.

3Underfitting, good fit, overfitting

  • Underfitting: too simple (a straight line through a curve). Wrong on training and new data.
  • Good fit: catches the real pattern, ignores the noise. Low error on both.
  • Overfitting: so flexible it bends through every training point, noise included. Tiny training error, wild mistakes on new data.
Two errors to know
Training error = loss on the data it trained on.
Test (generalization) error = loss on new data.
Overfitting: training ≪ test. Underfitting: both high.

As the model gets more flexible, training error keeps falling (more freedom always fits the points better). Test error falls at first, then rises again once the model starts fitting noise. The best model sits at the bottom of the test-error curve.

4Watching it happen (the demo)

Fit a polynomial $\hat{y}=w_0+w_1x+w_2x^2+\dots+w_kx^k$ to some noisy points and raise the degree $k$. Training error shrinks every time; past some point the curve starts wiggling to chase single points, and test error grows.

Example
12 training points and degree 11 → 12 parameters, so the curve can pass through every point exactly. Perfect training score, terrible model.

5Train / validation / test

The fix is simple and non-negotiable: judge the model on data it didn't train on. Split before doing anything else:

  • Training set (~70%): fit the model's parameters.
  • Validation set (~15%): compare models and pick settings (like the polynomial degree).
  • Test set (~15%): one final honest estimate. With huge datasets, validation and test can be a smaller share.
Why a separate validation set?
Try 20 models and keep whichever wins on the test set, and you've tuned to the test set: its score is now too optimistic. Choices happen on validation; the test set gives the final verdict. Both "wear out" the more you reuse them.

Rules for a good split

  • Shuffle first, unless it's a time series: then train on the past, test on the future.
  • The test set should look like real-world data (the same mix of cases).
  • No duplicates between training and test, or you're testing on memorised examples.
  • For classification, use a stratified split: each set keeps the same share of each class.

6k-fold cross-validation

Judging a restaurant by one meal is risky: maybe the chef had a bad night. Five meals tell you much more. With a small dataset, one validation split is like one meal: the score depends on which examples happened to land in it.

  1. Cut the training data into $k$ equal folds (usually 5 or 10).
  2. Train on $k-1$ folds, score on the one left out.
  3. Repeat so every fold is left out exactly once.
  4. Report the mean and the standard deviation of the $k$ scores.

$\text{CV score}=\dfrac{1}{k}\sum_{j=1}^{k}\text{score}_j$

Example
5 folds score 0.82, 0.85, 0.80, 0.84, 0.84 → mean $4.15/5=$ 0.83, with a small spread (about ± 0.02). Five models were trained, one per fold. Report it as 0.83 ± 0.02.

7Data leakage: the silent killer

Leakage = information from outside the training data sneaking into training, so the score looks better than reality. Classic ways it happens:

  • Preprocessing before splitting: computing the mean and standard deviation for scaling on all the data, test set included.
  • A feature that contains the answer: predicting whether a customer will cancel using a "cancellation fee charged" column.
  • Time travel: shuffling stock prices so the model trains on Wednesday to predict Tuesday.
  • Duplicates that end up in both training and test.
The golden rule
✗ scale everything → split
✓ split first → learn everything (scaling, feature choices, parameters) from training data only → just apply it to validation and test. Never call fit on the test data.

8Putting it all together

  1. Split off a test set and don't look at it.
  2. On the training set, use cross-validation (or a validation set) to compare models and settings.
  3. Pick the best one and retrain it on the full training set.
  4. Evaluate once on the test set and report that number.

★Going deeper: validation you can trust

The habits above (split, cross-validate, avoid leakage) quietly break in four common situations. Each one makes a model look great in testing and disappoint in production.

1. Tuning inflates the score → nested CV

Try many settings and keep the best cross-validated score, and that score is optimistic: some settings won partly by luck on these particular folds (like the best of 20 coin-flippers looking "skilled").

Nested cross-validation fixes it with two loops:

  • Inner loop: chooses the settings, using only the training part of each outer fold.
  • Outer loop: scores the whole "tune, then fit" recipe on data the tuning never saw.
Example from the lesson
An SVM tuned over 25 settings on a small, noisy dataset: the search reports 0.633, nested CV says 0.608. The gap grows with more settings and shrinks with more data.

To build the final model you still run the normal search on all the data; nested CV tells you how well that recipe will do.

2. Rows that aren't independent: time and groups

  • Time series: neighbouring days look alike. A shuffled split puts Tuesday in training and Wednesday in validation, so the model just "remembers" the nearby level.
  • Groups: several rows per customer, patient or house. If one customer is on both sides, the model learns that person, not the pattern.
Example from the lesson
Slowly drifting daily sales, random forest. Shuffled k-fold: $R^2=$ 0.957 (looks superb). Time-ordered split (TimeSeriesSplit): $R^2=$ −0.609, worse than predicting the average! The forest can't follow a drifting trend, and shuffling hid it.

For groups use GroupKFold (all of one group's rows on the same side).

Rule
Split the way the model will be used.

3. Would more data help? Learning curves

Train on growing subsets and plot training and validation scores against training-set size.

Example from the lesson
Breast-cancer data, logistic regression: validation accuracy climbs from 0.916 (22 examples) to 0.981 (455), and the gap to training (0.989) is now small.
  • Big gap, validation still rising (high variance) → more data will probably help.
  • Both low and close (high bias) → more data won't help much; use a more flexible model or better features.
  • Both high, flat and close → you're near the limit for this model and these features.

4. When the world changes: distribution shift

  • Covariate shift: the inputs change, the relationship stays (a new city with bigger homes).
  • Label shift: the class balance changes (more fraud in the holiday season).
  • Concept drift: the relationship itself changes (after a rule change, the same features mean something else). Needs fresh labels to detect.

Adversarial validation spots the first kind: label training rows 0 and new rows 1, then train a classifier to tell them apart. AUC near 0.5 → they look alike. Clearly higher → real shift, and the feature importances show where.

Example from the lesson
No shift: AUC 0.540, importances evenly spread. One feature drifted by 0.8 standard deviations: AUC 0.695, and that feature's importance jumps to 0.59, pointing straight at the culprit.

A validation checklist

  • Reporting a tuned model → nested CV, or a test set used once.
  • Data ordered in time → time-ordered splits, never shuffle.
  • Several rows per person, item or place → GroupKFold.
  • Rare classes → stratified splits.
  • Should we collect more data? → a learning curve.
  • New data might differ → adversarial validation and drift monitoring.
✎ in one line: fit on train, choose with validation or CV, judge once on test, and never let the test data leak in.
