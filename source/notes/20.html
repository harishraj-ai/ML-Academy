Part 5 · Lesson 20

Feature engineering, pipelines & final project

1Data beats algorithms

Models want a neat table of numbers. Real data has gaps, text categories ("Chennai", "two-year contract"), amounts from 5 to 5 million, and dates. Turning it into good inputs is feature engineering, and it often matters more than the algorithm.

2Numeric features: scaling

Distance- and gradient-based models (kNN, SVM, linear/logistic regression, neural nets) need similar scales. Trees don't.

  • StandardScaler: $z=(x-\mu)/\sigma$. The usual default.
  • MinMaxScaler: squeeze into [0, 1].
  • RobustScaler: median and IQR, so outliers don't distort it.
Example
Tenure 3, 12, 24 months → mean 13, sd $\sqrt{74}\approx8.60$ → z-scores ≈ −1.16, −0.12, 1.28.

Very skewed amounts (balances 0 to 5,000,000, mostly small)? A log transform, e.g. np.log1p (handles zeros).

3Categorical features

House numbers vs light switches
Chennai = 1, Mumbai = 2, Delhi = 3 would mean Delhi is "3 × Chennai" and Mumbai lies "between". One-hot gives each city its own on/off switch.

One-hot: one 0/1 column per category, exactly one 1 per row; all categories equally different. OneHotEncoder(handle_unknown="ignore"): a city never seen in training (Kolkata) becomes all zeros instead of an error.

Ordered categories (small < medium < large) can use ordinal codes.

4Missing values

  • Drop rows: only if very few are missing at random.
  • Impute (SimpleImputer): median (numbers), most frequent (categories), or a constant like "unknown"; KNNImputer borrows from similar rows.
  • Add a "was missing" indicator: missingness itself can be informative.
Imputation can leak too: the median must come from the training data only. Pipelines handle this.

5Creating new features

  • Ratios / differences: price per m², debt-to-income, charge per support call.
  • Dates: weekday, month, hour, weekend, days since last purchase (raw timestamps rarely help).
  • Interactions: products of features (PolynomialFeatures).
  • Aggregates: average order value, orders in the last 30 days.
  • Text: word counts or TF-IDF.
Think like the model
"If I were predicting this by hand, what would I want to know?" E.g. "days until due" for late payments.

6Feature selection

Remove near-constant features (VarianceThreshold), keep the best by a test (SelectKBest), keep what a model rates important (SelectFromModel, e.g. Lasso), or let L1 zero them out. Always inside the pipeline.

7The pipeline demo

Edit a raw customer table and watch the matrix the model receives: missing charge filled with the training median, numbers standardised, contract one-hot encoded. The statistics are exactly what fit learns.

8Pipelines done right

A Pipeline chains steps into one model object; a ColumnTransformer applies different steps to different columns. Three huge benefits:

  1. No leakage: everything is learned from training data, and re-learned inside every CV fold.
  2. One object to tune: grid search can tune preprocessing and model together (e.g. model__C).
  3. One object to deploy: raw data in, prediction out, with no "training/serving skew".

9Final project: customer churn

A telecom company wants to know who's likely to cancel, to offer them a deal first. A synthetic 2,000-customer dataset (patterns built in, so it illustrates the workflow, not real behaviour): 40% churned, two columns with gaps (105 and 86 missing), three text categories.

  1. Load and explore.
  2. Split before anything else (400 test customers locked away).
  3. Build the pipeline (impute, scale, one-hot).
  4. Score a trivial baseline, then compare models with cross-validation.
  5. Tune the best, evaluate once on the test set, choose a threshold.
  6. Interpret and save the whole pipeline.

10After deployment: monitoring

Performance can quietly decay as the world changes. "Watch for silent failures": a feature filled for 90% of rows dropping to 60% because an upstream system changed.

  • Log inputs and predictions; track feature and probability distributions.
  • Measure real-world metrics when outcomes arrive.
  • Check for training/serving skew.
  • Retrain on recent data; evaluate on later data.

11The whole workflow

define problem & metric → explore → split (by time if needed) → pipeline → baseline → compare with CV → tune → test once & threshold → interpret → save, deploy, monitor

★Going deeper: leak-proof pipelines and efficient tuning

Target encoding: how much leakage can fake

Imagine telling a student the class average for a question, where that average includes their own answer. With 30 students it's a tiny hint. With only 2 students it practically gives the answer away. Target encoding with many rare categories does exactly that.

A rare category gives the answer away
A postcode appears in 2 rows, with targets 1 and 1.
Its average target is 1.0, so the "feature" is just the answer.
Encode each row with the other rows only (cross-fitting) and that row's own label can't leak in.

One pipeline for mixed data

Different ingredients need different preparation: wash the vegetables, slice the bread, grate the cheese. ColumnTransformer gives each kind of column its own preparation, all inside one recipe.

Grid search vs random search

If only one of three settings really matters, a 3×3×2 grid tries just 3 different values of it, wasting most tries. Random search tries a new value of every setting each time, so 18 tries test 18 values of the one that matters.

Keeping track of experiments

A lab notebook. A scientist writes down every experiment: what was used, what was done, what happened. Months later anyone can repeat the best one. ML projects need the same, because after a few weeks there are hundreds of runs.

In one breath
Do target encoding inside the pipeline with cross-fitting, or it can fake accuracy on pure noise; give each column type its own preprocessing in one ColumnTransformer; prefer random (or Bayesian) search to grids; and log every experiment so the winning model can be rebuilt.
✎ in one line: good features plus one Pipeline fitted on training data give honest scores and safe deployment.
