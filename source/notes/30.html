MLOps: deploying & monitoring

1From notebook to production

A model in a notebook helps nobody. It creates value when it runs reliably, every day, on new data, inside a product, and keeps working as the world changes. MLOps: packaging and versioning, checking inputs, serving, monitoring drift, retraining, and testing ML code like any software.

The core idea
Treat a model as a product that decays. Make every version reproducible and traceable, and watch it once it's live.

2The life cycle

  1. Develop: data, features, model, offline evaluation.
  2. Package and version: the fitted pipeline + metadata (data, code and library versions, metrics).
  3. Validate inputs against the expected schema.
  4. Serve: batch (score everyone nightly) or online (an API in milliseconds).
  5. Monitor: input drift, prediction drift, real performance once labels arrive.
  6. Retrain and redeploy: on a schedule or a trigger, with tests and a gradual rollout.

3Packaging and versioning

  • Save the whole pipeline, never just the model. Re-implementing preprocessing in production is a classic bug.
  • Store metadata: version, expected features, test metrics, library versions, and a fingerprint (hash) to prove which model made a prediction.
  • After saving, reload and check the predictions are identical.
  • Pin versions (requirements.txt or a container): a model saved with one scikit-learn may not load with another.

Model registries (MLflow) keep files, metadata and stages ("staging", "production").

4Validating inputs

Live data is messier: missing fields, wrong types, units changed upstream, impossible values. A model happily returns a confident prediction for nonsense.

Example from the lesson
Caught before the model: a missing debt value, a negative income, a number sent as text, an age of 230.

Decide in advance: reject, use a safe default, or send to a person. Log bad rows: a sudden rise means something broke upstream.

5Data drift

  • PSI (population stability index): bin by training quantiles, sum $(a-e)\ln(a/e)$. Below 0.1 stable · 0.1–0.25 watch · above 0.25 major shift.
  • Kolmogorov–Smirnov: the biggest gap between the two cumulative distributions. With big samples tiny shifts look "significant", so look at its size too.
Example
Live incomes have fallen: PSI 0.612 (major), KS statistic 0.312.

6The drift demo

Shift the live data's mean or change only its spread: a change in spread with the same average is caught too.

7Concept drift and retraining

Inputs look the same but the input → outcome relationship changes (after an economic shock, the same income means different risk). Only real outcomes reveal it.

Example
From month 5 the effect of income fades then reverses. Never-retrained model: AUC 0.82 → 0.41 (worse than guessing). Retrained monthly: recovers to 0.83, a month behind.

Retrain on a schedule, or on triggers (drift or performance crossing a threshold). Validate the new model against the current one on recent data, and keep a rollback ready.

8Testing ML code

  • Unit tests: does the feature function handle missing values?
  • Minimum quality: the metric stays above a bar on a fixed test set.
  • Directional: "more debt should never lower the predicted risk".
  • Invariance: something that shouldn't matter (or mustn't, like a protected attribute) doesn't change the prediction much.

Run them automatically (pytest in CI) on every change to code, data or model; a failing test blocks deployment.

9Serving and rollout

  • Batch scoring: daily churn lists, weekly forecasts.
  • Online API (FastAPI, Flask): fraud checks at checkout, recommendations.
  • Shadow: the new model scores live traffic silently, for comparison.
  • Canary / A/B: a small share of traffic first, increased if it performs.
Log every prediction
Input, output, model version, timestamp: for debugging, monitoring, joining with outcomes for retraining, and audits.

★Going deeper: drift alarms and champion–challenger tests

Significant is not the same as important

With a precise enough scale, you can prove a bag of sugar weighs 0.1 g less than last week. True, and completely unimportant. Huge samples make tests "significant" for tiny changes; what matters is how big the change is.

Reading it
500 rows: p = 0.158, no alarm.
50,000 rows: the same tiny shift gives $p\approx10^{-6}$, an alarm about nothing.
PSI stays tiny (below 0.03) throughout: it measures size, so it isn't fooled.

Is the challenger really better?

A new player scores two more goals than your star in one friendly match. Before dropping your star, ask whether that gap is bigger than ordinary match-to-match luck.

Reading it
Challenger AUC 0.728 vs champion 0.725: +0.003.
95% interval for the improvement: −0.022 to +0.027.
It includes 0 (and negative values), so the data can't tell them apart.
In one breath
Judge drift by its size (PSI, shift in standard deviations), not by p-values that alarm on anything with enough data; and replace the champion only when the bootstrap interval for the improvement is clearly above zero.
