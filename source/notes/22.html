SQL & data wrangling for ML

1Why SQL?

In a real job the data isn't one tidy table: it lives in a database, spread across many tables (customers, orders, payments, tickets), often with millions of rows. Someone has to pull the right rows, join, summarise events into features, and not peek into the future. That's usually you, in SQL. Data-science interviews almost always include a SQL round.

2Tables, rows and keys

  • Primary key: uniquely identifies a row (houses.id).
  • Foreign key: points to another table's primary key (viewings.house_id).

Viewings get their own table so a house can have 0, 1 or 50 without empty columns: normalisation. Building ML features is mostly the reverse: denormalising back into one wide row per entity.

3SELECT, WHERE, ORDER BY

SELECT columns FROM table WHERE condition ORDER BY column

  • pd.read_sql runs a query and returns a DataFrame.
  • Extras: LIMIT, DISTINCT, AND/OR, IN (…), BETWEEN, LIKE 'new%'.
  • Missing = NULL → use IS NULL; = NULL is never true.

4GROUP BY: rows → summaries

Collapse rows sharing a value; summarise with COUNT, SUM, AVG, MIN, MAX.

WHERE vs HAVING
WHERE filters rows before grouping. HAVING filters groups after (HAVING COUNT(*) >= 3).
Example from the lesson
Outskirts homes: prices 84, 42, 50 lakh; sizes 150, 95, 130 m².
COUNT = 3; AVG(price) = 176/3 ≈ 58.7.
AVG(price/size) = average of 0.560, 0.442, 0.385 ≈ 0.462, but total price ÷ total size = 176/375 = 0.469. Average of ratios ≠ ratio of totals.

5Joins

Example from the lesson
12 houses, only 7 had viewings. INNER join → 7 rows (the other 5 vanish). LEFT join → all 12, with 0 viewings for the unviewed.

An inner join silently drops entities (often the unusual ones), and "zero viewings" is useful information.

One-to-many trap: join houses to viewings, then AVG(price) → a house with 10 viewings counts 10 times. Aggregate the "many" side first, then join. Check row counts after every join.

6The join demo

Switch INNER/LEFT and grouping on/off: watch houses disappear, get NULLs, or repeat until grouped.

7Window functions

Compute across related rows without collapsing them: OVER (PARTITION BY … ORDER BY …).

Example
RANK() OVER (PARTITION BY area ORDER BY price DESC) and price - AVG(price) OVER (PARTITION BY area): house 3 is 18.3 lakh above the Central average; house 4 is 21.4 below the Suburb average.

Also ROW_NUMBER(), LAG(x) (previous value: "change since last month"), and running totals over a frame.

8The same in pandas

  • WHERE → df[df.price > 80] or df.query(…)
  • GROUP BY → df.groupby("area").agg(…)
  • LEFT JOIN → left.merge(right, on=…, how="left")
  • window AVG → groupby(…)["x"].transform("mean")
  • ORDER BY … LIMIT 5 → df.nlargest(5, "x")

Central homes average 1.25 viewings, Outskirts 0.33. Rule of thumb: filter and join in the database, finish in pandas.

9Reshaping and cleaning

  • Long vs wide: events are long (one row per house per day); models need wide. pivot_table / melt.
  • Types: numbers as text, dates as strings → pd.to_numeric, pd.to_datetime.
  • Duplicates: check df.id.is_unique before and after joins.
  • Missing can mean zero, unknown or not applicable: decide deliberately.

10Point-in-time correctness

Predicting on day 5 with "number of viewings": counting all viewings includes days 6–9, information the model won't have in real use.

Example
All time: 11 viewings. Before day 5: only 6.
The golden rule
Put the time condition inside the join, so every feature uses only data from before that row's prediction time.

★Going deeper: indexes, NULL logic and rolling features

Indexes and query plans

Finding every mention of "tax" in a book: read every page (a full scan) or look it up in the index at the back and jump straight to the right pages. A database index works the same way.

Scan vs index
200,000 viewings. A full scan checks all 200,000 rows.
A B-tree index halves the search at each level: about $\log_2(200{,}000)\approx18$ steps to reach house 42.
Then it reads just that house's 37 rows.

NULL: three-valued logic

Ask "is the unknown discount bigger than 5?" The honest answer is "don't know". Ask "is it NOT bigger than 5?" Still "don't know". SQL keeps only rows where the answer is a definite yes, so rows with unknown values drop out of both questions.

Reading each line
discount > 5: row 1 (10). Rows 2 and 4 are unknown, so dropped.
NOT (discount > 5): only row 3. "Not unknown" is still unknown, so rows 2 and 4 vanish again.
discount = NULL: nothing, ever. Use IS NULL: rows 2 and 4.
AVG(discount) $=(10+0)/2=5.0$: the NULLs are skipped. Treating missing as 0 would give $(10+0+0+0)/4=2.5$.

Rolling features with window frames

A 7-day rolling total is a sliding window: today plus the six days before. Slide it forward one day and the oldest day falls out while the newest comes in. LAG simply looks one row back.

Day 9's 7-day total
Window = days 3 to 9.
Views: $1+0+3+1+0+0+4=9$.
Day 1 has no previous day, so views_yesterday is NULL (NaN in pandas).
In one breath
Index the columns you filter and join on and read the query plan; remember NULL makes comparisons unknown, so handle missing values explicitly; and build rolling features with window frames that only look at the past.
✎ in one line: LEFT JOIN to keep everyone, aggregate before joining, mind the NULLs, and use only the past.
