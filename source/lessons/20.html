Data beats algorithms

Every model in this course expects a neat table of numbers: no gaps, no text, sensible scales. Real data is never like that. It has missing values, categories like "Chennai" or "two-year contract", amounts that range from 5 to 5 million, and dates. Turning raw data into good model inputs is called feature engineering, and in practice it often matters more than which algorithm you choose.

This final lesson covers the essential techniques, then shows how to package every step into a pipeline that is safe from data leakage. It ends with a complete project — from raw data to a saved, tested model — that puts the whole course together.

Numeric features

Scaling

From Lessons 7, 10, 11 and 15: distance-based and gradient-based models (kNN, SVMs, linear and logistic regression, neural networks) need features on similar scales. Tree models (Lessons 13–14) don't.

  • Standardisation (StandardScaler): $z = (x - \mu)/\sigma$ — mean 0, standard deviation 1. The usual default.
  • Min–max scaling (MinMaxScaler): $x' = (x - x_{\min})/(x_{\max} - x_{\min})$ — squeezes into $[0, 1]$.
  • Robust scaling (RobustScaler): uses the median and interquartile range, so outliers don't distort it.
Worked example — standardising tenure

Three customers have been with the company 3, 12 and 24 months. Mean $\mu = 13$. Standard deviation $\sigma = \sqrt{\frac{(-10)^2 + 1^2 + 11^2}{3}} = \sqrt{74} \approx 8.60$.

z-scores: $\frac{3-13}{8.60} \approx -1.16$, $\ \frac{12-13}{8.60} \approx -0.12$, $\ \frac{24-13}{8.60} \approx 1.28$.

Crucially, $\mu$ and $\sigma$ are computed on the training set only, then reused unchanged on the test set and on new data.

Transforming skewed values

Amounts like income, prices or total spending are often skewed: most values are small, a few are huge. A log transform compresses the range so the huge values don't dominate: 100, 1,000 and 10,000 become 2, 3 and 4 with $\log_{10}$. In code, np.log1p(x) computes $\ln(1 + x)$, which also handles zeros safely.

Binning

Sometimes it helps to turn a number into ranges (age 18–25, 26–40, …) — useful when the effect isn't smooth, or for readability. It throws away detail, so use it deliberately.

Categorical features

Models need numbers, but you can't just number the categories (Chennai = 1, Mumbai = 2, Delhi = 3): the model would think Delhi is "three times" Chennai, and that Mumbai lies "between" them.

One-hot encoding

Create one 0/1 column per category; exactly one is 1 for each row.

Worked example
city→city_Chennaicity_Delhicity_Mumbai
Chennai100
Mumbai001
Delhi010

All categories are now equally different from each other. In scikit-learn: OneHotEncoder(handle_unknown="ignore") — the option means a category never seen in training (say "Kolkata") becomes all zeros instead of an error.

Ordinal encoding

When categories have a natural order (small < medium < large; month-to-month < one-year < two-year), mapping them to 0, 1, 2 keeps that order in one column (OrdinalEncoder). Fine for trees; for linear models it assumes equal steps between levels.

Many categories

A feature like "postcode" may have thousands of values, which would create thousands of columns. Options include grouping rare categories into "other", or target encoding (replacing each category by the average label for that category — computed carefully inside cross-validation, or it leaks).

Missing values

Most scikit-learn models refuse missing values (HistGradientBoosting is an exception). Choices:

  • Drop rows — only if very few are missing and missingness is random. Otherwise you lose data and may bias the sample.
  • Impute — fill in a value with SimpleImputer: the median (robust for numbers), mean, most frequent (for categories), or a constant like "unknown". KNNImputer fills values from similar rows.
  • Add a "was missing" indicator (add_indicator=True). Missingness itself can carry information: a customer who didn't give a phone number may behave differently.
Imputation can leak too

The median used for filling gaps must be computed from the training data only — just like scaling statistics. Pipelines handle this automatically.

Creating new features

Often the most valuable features are ones you build from domain knowledge:

  • Ratios and differences: price per m², debt-to-income, monthly charge per support call.
  • Dates: from a timestamp, extract day of week, month, hour, "is weekend", or "days since last purchase". Raw timestamps are rarely useful directly.
  • Interactions: products of features (e.g. PolynomialFeatures) let linear models capture combined effects.
  • Aggregates: a customer's average order value, number of orders in the last 30 days.
  • Text: word counts (CountVectorizer, Lesson 12) or TF-IDF weights, which down-weight words common to every document.
Think like the model

Ask: "If I were predicting this by hand, what would I want to know?" A model predicting late payments benefits from "days until due date" far more than from two separate raw dates.

Feature selection

More features isn't always better (Lessons 10, 11, 17). Ways to keep only useful ones: remove near-constant features (VarianceThreshold), keep the best by a statistical test (SelectKBest), keep features a model rates as important (SelectFromModel, e.g. with Lasso), or let L1 regularization zero out the rest. Like all preprocessing, do it inside the pipeline.

Pipelines: preprocessing done right

A Pipeline chains steps into a single model object. A ColumnTransformer applies different steps to different columns. Together they give you three huge benefits:

  1. No leakage. Calling fit learns imputation values, scaling statistics and encodings from the training data only. During cross-validation, they're re-learned inside every fold.
  2. One object to tune. Grid search can tune preprocessing and model settings together (e.g. model__C).
  3. One object to deploy. Raw data in, prediction out — exactly the same transformations in training and production. Mismatches between the two ("training/serving skew") are a classic source of silent bugs.

Final project: predicting customer churn

The problem: a telecom company wants to know which customers are likely to cancel ("churn") so it can offer them a deal first. The table has numbers, categories and missing values — like real data. So that you can run everything yourself without downloading anything, the code first generates a realistic dataset of 2,000 customers. (It's synthetic: the patterns were built in, so they illustrate the workflow rather than real customer behaviour.)

Step 1 — Load and explore the data

import numpy as np
import pandas as pd

rng = np.random.default_rng(42)
n = 2000
df = pd.DataFrame({
    "tenure_months": rng.integers(1, 73, n),
    "monthly_charge": rng.normal(65, 20, n).clip(15, 130).round(2),
    "support_calls": rng.poisson(1.5, n),
    "contract": rng.choice(["month-to-month", "one-year", "two-year"], n, p=[0.55, 0.25, 0.20]),
    "payment": rng.choice(["card", "bank", "check"], n, p=[0.4, 0.35, 0.25]),
    "city": rng.choice(["Chennai", "Mumbai", "Delhi", "Pune"], n),
})
df["total_spent"] = (df["tenure_months"] * df["monthly_charge"] * rng.normal(1, 0.05, n)).round(2)
score = (-2.0 + 1.6 * (df["contract"] == "month-to-month") - 0.035 * df["tenure_months"]
         + 0.018 * df["monthly_charge"] + 0.45 * df["support_calls"] + 0.5 * (df["payment"] == "check"))
df["churned"] = (rng.random(n) < 1 / (1 + np.exp(-score))).astype(int)
for col, frac in [("monthly_charge", 0.05), ("payment", 0.04)]:     # real data has gaps
    df.loc[rng.random(n) < frac, col] = np.nan

print(df.shape)
print(df.head(3).to_string())
print("churn rate:", round(df["churned"].mean(), 3))
print(df.isna().sum()[df.isna().sum() > 0].to_dict())

Step 2 — Split before anything else

from sklearn.model_selection import train_test_split

X = df.drop(columns="churned")
y = df["churned"]
X_train, X_test, y_train, y_test = train_test_split(X, y, test_size=0.2, stratify=y, random_state=0)

The test set (400 customers) is now locked away until Step 6 (Lesson 5).

Step 3 — Feature engineering and preprocessing

from sklearn.compose import ColumnTransformer
from sklearn.pipeline import Pipeline
from sklearn.impute import SimpleImputer
from sklearn.preprocessing import StandardScaler, OneHotEncoder, FunctionTransformer

def add_features(X):
    X = X.copy()
    X["charge_per_call"] = X["monthly_charge"] / (X["support_calls"] + 1)   # a ratio feature
    X["log_total_spent"] = np.log1p(X["total_spent"])                       # tame the skew
    return X

numeric = ["tenure_months", "monthly_charge", "support_calls", "total_spent",
           "charge_per_call", "log_total_spent"]
categorical = ["contract", "payment", "city"]

preprocess = ColumnTransformer([
    ("num", Pipeline([("impute", SimpleImputer(strategy="median")),
                      ("scale", StandardScaler())]), numeric),
    ("cat", Pipeline([("impute", SimpleImputer(strategy="most_frequent")),
                      ("onehot", OneHotEncoder(handle_unknown="ignore"))]), categorical),
])

Numbers: fill gaps with the median, then standardise. Categories: fill gaps with the most common value, then one-hot encode. Nothing is fitted yet — that happens inside cross-validation.

Step 4 — Start with a baseline, then compare models

from sklearn.dummy import DummyClassifier
from sklearn.linear_model import LogisticRegression
from sklearn.ensemble import RandomForestClassifier, HistGradientBoostingClassifier
from sklearn.model_selection import cross_val_score

candidates = {
    "baseline (majority)": DummyClassifier(strategy="most_frequent"),
    "logistic regression": LogisticRegression(max_iter=1000),
    "random forest": RandomForestClassifier(n_estimators=300, random_state=0),
    "gradient boosting": HistGradientBoostingClassifier(random_state=0),
}
for name, clf in candidates.items():
    pipe = Pipeline([("features", FunctionTransformer(add_features)),
                     ("prep", preprocess), ("model", clf)])
    s = cross_val_score(pipe, X_train, y_train, cv=5, scoring="roc_auc")
    print(f"{name:22s} ROC-AUC {s.mean():.3f} ± {s.std():.3f}")
baseline (majority)    ROC-AUC 0.500 ± 0.000
logistic regression    ROC-AUC 0.771 ± 0.008
random forest          ROC-AUC 0.756 ± 0.010
gradient boosting      ROC-AUC 0.739 ± 0.008

We use ROC-AUC (Lesson 9) because we'll want to rank customers by risk. The baseline scores 0.5 — pure guessing — so everything above it is real signal. Interesting: logistic regression beats the ensembles here. The relationships in this data are close to linear on the log-odds scale (Lesson 8), so the simpler model fits them best and the flexible models only add variance. Always compare — don't assume the fanciest model wins.

Step 5 — Tune the best model

from sklearn.model_selection import GridSearchCV

pipe = Pipeline([("features", FunctionTransformer(add_features)), ("prep", preprocess),
                 ("model", LogisticRegression(max_iter=1000))])
search = GridSearchCV(pipe, {"model__C": [0.01, 0.1, 1, 10]}, cv=5, scoring="roc_auc")
search.fit(X_train, y_train)
print("best C:", search.best_params_["model__C"], " CV ROC-AUC:", round(search.best_score_, 3))
best C: 0.1  CV ROC-AUC: 0.772

Slightly stronger regularization ($C = 0.1$, Lesson 10) helps a little.

Step 6 — Evaluate once on the test set

from sklearn.metrics import roc_auc_score, classification_report

best = search.best_estimator_
proba = best.predict_proba(X_test)[:, 1]
print("test ROC-AUC:", round(roc_auc_score(y_test, proba), 3))
print(classification_report(y_test, (proba >= 0.5).astype(int), target_names=["stayed", "churned"]))

Because features were standardised, the coefficients are comparable (Lesson 6). Month-to-month contracts and more support calls push towards churn; longer tenure and annual contracts push away. These match the patterns built into the data — a good sanity check. Remember: these describe associations, not proven causes.

Step 8 — Save, reload and predict

import joblib

joblib.dump(best, "churn_model.joblib")
reloaded = joblib.load("churn_model.joblib")       # only ever load files you trust!

new_customer = pd.DataFrame([{"tenure_months": 3, "monthly_charge": 95.0, "support_calls": 4,
                              "contract": "month-to-month", "payment": "check", "city": "Pune",
                              "total_spent": 285.0}])
print("churn probability:", round(reloaded.predict_proba(new_customer)[0, 1], 3))
churn probability: 0.958

The whole pipeline — feature creation, imputation, scaling, encoding and model — is saved as one file. Raw customer data goes in, a probability comes out. A new, expensive, month-to-month customer with 4 support calls is flagged as very high risk.

One practical detail

The saved file stores a reference to the add_features function, not its code. To load the model in a different script or server, that function must be importable there too — for example, put it in a small module file (features.py) and import it in both places.

Security: loading model files

scikit-learn's documentation warns that pickle-based formats (pickle, joblib) can execute arbitrary code when loaded. Never load a model file from a source you don't trust. Safer formats include skops.io (which lets you inspect untrusted types before loading) and ONNX. Pickle-based files also need the same library versions that were used to save them.

After deployment: monitoring

A model's performance can quietly decay because the world changes (Lesson 5's distribution shift). Google's Rules of Machine Learning warns to "watch for silent failures" — for example, a feature that used to be filled in for 90% of rows dropping to 60% because an upstream system changed. In practice:

  • Log inputs and predictions; track the distribution of each feature and of the predicted probabilities over time.
  • When true outcomes arrive (did the customer actually leave?), keep measuring real-world metrics.
  • Check for training/serving skew: is production data processed exactly like training data?
  • Retrain regularly on recent data, and evaluate on data from later than the training period.

The complete ML workflow — a checklist

  1. Define the problem, the label and the metric that reflects real costs.
  2. Collect and explore the data: types, gaps, imbalance, oddities.
  3. Split off a test set immediately (by time, if the data is time-ordered).
  4. Build a pipeline: feature engineering, imputation, encoding, scaling.
  5. Score a trivial baseline.
  6. Compare several model families with cross-validation.
  7. Tune the best one or two.
  8. Evaluate once on the test set; choose a decision threshold.
  9. Interpret and sanity-check the model.
  10. Save the whole pipeline, deploy, and monitor.

Key takeaways

  • Good features often matter more than the choice of algorithm.
  • Scale numbers for distance/gradient models, log-transform skewed amounts, one-hot encode categories, and impute missing values (optionally with an indicator).
  • Create features from domain knowledge: ratios, date parts, aggregates.
  • Put everything in a Pipeline + ColumnTransformer so it's fitted on training data only and deployed as one object.
  • Workflow: split → baseline → compare with CV → tune → test once → interpret → save → monitor.

Check your understanding

1. Why not encode cities as Chennai = 1, Mumbai = 2, Delhi = 3 for a linear model?

Arbitrary numbers impose a fake order and spacing. One-hot encoding treats categories as equally different.

2. Where should the median used to fill missing values come from?

Like all learned preprocessing statistics, it must come from training data to avoid leakage.

3. A column holds account balances from 0 to 5,000,000, mostly under 10,000. A sensible transformation is…

The log compresses the huge range so a few extreme values don't dominate. log1p also handles zeros.

4. What is the main advantage of putting preprocessing inside a Pipeline?

Pipelines prevent leakage and guarantee identical processing in training and deployment.

5. Your new model scores ROC-AUC 0.52 and the baseline scores 0.50. What does that tell you?

Always compare with a baseline; a tiny improvement over random ranking means little useful signal has been captured.
